## ✔️ Update: `{name}` placeholder must be renamed for autocomplete to work

During additional testing, it became clear that `{name}` is only a placeholder
generated by the editor. Autocomplete behaves normally **only after `{name}` is
replaced with a real input name**.

**Observed behavior (expected):**
- As long as an input block starts with `{name}:`
  - autocomplete under `inputs:` shows only `new input`
  - inner autocomplete is limited or missing
- After renaming `{name}` to a real field name (e.g. `customerId:`)
  - autocomplete works correctly everywhere
  - suggestions for `required`, `type`, and `debugValue` appear as expected

**Conclusion:**  
This is intended behavior. `{name}` must be replaced immediately for the inputs
section to support full autocomplete.

## 5. Cancelling the task-creation dialog breaks autocomplete positioning

### 5.1 Test scenario

Starting with a fresh `tasks` block:

```yaml
tasks:
 'autocomplete here'
```

**Action:**
1. On a new line under `tasks:`, use autocomplete → suggestions appear:
   - `new decision task`
   - `new service task`
   - `new switch task`

2. Select **`new decision task`** *or* **`new service task`**.

3. A dialog window appears (task creator).  
   User presses **Cancel**.

---

### 5.2 Actual behavior

After cancelling the dialog:

- The cursor jumps to the **start** of the line.
- Autocomplete **stops working** at this position.

- The user must enter a **space character** manually before autocomplete begins suggesting:
  - `new decision task`
  - `new service task`
  - `new switch task`

---

### 5.3 Why this is a problem

- Users may think autocomplete “broke” or the line became invalid.
- The editor treats the cursor-at-start-of-line as incorrect indentation/context.
- It disrupts expected workflow:  
  cancelling a dialog should **not** erase context or break autocomplete.
- Requiring a manual space is unintuitive and inconsistent with other blocks.

---

### 5.4 Expected behavior

- After pressing **Cancel**, the cursor should:
  - remain in the correct indentation for a task list (`<two spaces> - `)
  - or at least remain at the **same position** where autocomplete was previously triggered

- Autocomplete should continue suggesting the three task options without requiring the user to insert a space.

---

### 5.5 Status

**Status:** ❌ **Bug – cancelling the task dialog resets cursor context and breaks autocomplete until a space is manually added**

## 7. UNDO does not revert task blocks inserted via autocomplete

### 7.1 Test scenario

Inside a `tasks:` section, using autocomplete allows insertion of these task blocks:

- `new decision task`
- `new service task`
- `new switch task`

Each of these inserts a **multi-line YAML structure** in one step.

### 7.2 Actual behavior

Using the editor's **UNDO shortcut (Ctrl+Z / Cmd+Z)**:

- ✔️ **Value edits** inside tasks (e.g., editing `id`, `ref`, `type`, etc.) are correctly undone.
- ❌ **The entire task blocks inserted via autocomplete are *not* undone.**

When an autocomplete block is inserted, pressing UNDO:

- does **not** remove the inserted block  
- does **not** restore the previous YAML structure  
- appears to do nothing unless the user performed additional edits afterward

This makes the inserted task blocks effectively “sticky,” requiring manual deletion.

### 7.3 Why this is a problem

- Users expect UNDO to reverse **their last action**, especially when the last action inserted 10+ lines.
- Inserting a task block is a **single operation**, but the undo history does not treat it as one.
- This inconsistency makes UNDO feel unreliable:
  - Editing a *value* is undoable  
  - Inserting a *block* via autocomplete is not undoable  
- Users may accidentally insert a task and have no quick way to revert.

### 7.4 Expected behavior

- Pressing UNDO immediately after inserting:
  - `new decision task`
  - `new service task`
  - `new switch task`

…should completely remove the generated block and return the editor to the state before insertion.

In other words, the entire insertion should be treated as **one atomic undo step**.

### 7.5 Status

**Status:** ❌ **Bug – autocomplete-inserted task blocks cannot be undone**

UNDO should work consistently for both inline edits and block insertions.

## 8. Switching between tabs in TheWrench causes autocomplete duplication

### 8.1 Test scenario

With one or more service flows open in the Flow Editor:

- Autocomplete initially behaves correctly (no duplicates).
- Navigate away from the Flow Editor by clicking **any tab except another Service Flow**.  
  This includes:
  - Service Flows (parent list view)
  - Decision Tables
  - Services
  - Debug
  - Compare
  - Activities
  - Any other top-level or secondary tab not representing an open flow

Switch back to the original open Flow Editor tab afterward.

---

### 8.2 Actual behavior

After switching to **any tab that is NOT another open service flow**, returning to the Flow Editor causes autocomplete to show **duplicated suggestions**.

Examples of duplicated categories:

- flow input suggestions  
- task outputs  
- structural suggestions like `inputs block`    

The duplication is consistent and affects all autocomplete categories.

---

### 8.3 Duplication increases with repeated tab switching

Each time the user:

1. Leaves the Flow Editor by switching to **any non-flow tab**, and  
2. Then returns to the Flow Editor  

…the autocomplete list accumulates **additional duplicate entries**.

This causes exponential growth, for example:

- `flow input: shouldBeQuestionnaireId`  
- `flow input: shouldBeQuestionnaireId`  
- `flow input: shouldBeQuestionnaireId`  
- `flow input: shouldBeQuestionnaireId` *(grows each switch)*

The same happens for:
- task outputs  
- “new input”  
- “inputs block”  
- task types  

---

### 8.4 What does *not* cause duplication

Switching **between open service flows specifically** does **not** trigger duplication.  
This is the only navigation case that behaves correctly.

All other tabs cause duplication.

---

### 8.5 Reset behavior

A **full page reload** clears all accumulated duplicates.  
Autocomplete then behaves correctly again until tab switching resumes.

---

### 8.6 Why this is problematic

This suggests autocomplete providers or data sources are being:

- re-registered  
- re-attached  
- or re-subscribed  

…every time a non-flow tab is opened.

But these registrations are **not removed** when returning to the Flow Editor.

The result:

- noisy, bloated autocomplete lists  
- inconsistent editor state  
- reduced reliability and UX clarity  
- higher cognitive load for users trying to select correct suggestions

---

### 8.7 Expected behavior

- Navigation between *any* tabs in TheWrench should **not** affect autocomplete state.
- The autocomplete suggestion list should:
  - remain stable  
  - contain only unique entries  
  - not grow exponentially  
- Open flows should retain correct autocomplete regardless of navigation.

---

### 8.8 Status

**Status:** ❌ **Bug – switching to any tab except another open service flow causes repeated autocomplete duplication**

This is a systemic autocomplete-provider lifecycle issue triggered by tab navigation.
