## ✔️ Update: `{name}` placeholder must be renamed for autocomplete to work

During additional testing, it became clear that `{name}` is only a placeholder
generated by the editor. Autocomplete behaves normally **only after `{name}` is
replaced with a real input name**.

**Observed behavior (expected):**
- As long as an input block starts with `{name}:`
  - autocomplete under `inputs:` shows only `new input`
  - inner autocomplete is limited or missing
- After renaming `{name}` to a real field name (e.g. `customerId:`)
  - autocomplete works correctly everywhere
  - suggestions for `required`, `type`, and `debugValue` appear as expected

**Conclusion:**  
This is intended behavior. `{name}` must be replaced immediately for the inputs
section to support full autocomplete.

## 2. Tasks block – “new decision task” autocomplete issues

---

### 2.2 Incorrect autocomplete inside the decision task

**Observation:**
Inside the `TestingDecision` task block, autocomplete behaves incorrectly:

- On the **`- TestingDecision:`** line:
  - Autocomplete **does work**, but the suggestions are clearly wrong.
  - It offers options that belong to the previous context (e.g. values from `type: STRING` in the `inputs` block).
  - These suggestions are not relevant for a task kind / node type.

- On the **`decisionTable:`** line:
  - Autocomplete also **shows suggestions**, but again they seem to come from the previous input context (`type: STRING` etc.).
  - These suggestions do not make sense for a `decisionTable` key.

- On other lines inside the block (e.g. `id:`, `then:`, `ref:`, `collection:`, `inputs:`, `inputColumn:`):
  - Autocomplete **does not offer the expected context-aware suggestions**.

**Expected behavior:**
- For the `- TestingDecision:` line:
  - Either no autocomplete at all, or suggestions relevant to **task types**.
- For the `decisionTable:` line:
  - Probably **no autocomplete**, or autocomplete that is specific to decision-table structures.
- In any case:
  - These lines **should not** be receiving suggestions copied from the previous `type: STRING` context.

**Status:** ❌ **Bug – autocomplete context is wrong inside decision task**
- Autocomplete in the decision task appears to “reuse” the previous input-field context (`type: STRING`) instead of using a task-/decision-specific context.
- This leads to irrelevant suggestions on lines like `TestingDecision:` and `decisionTable:` where autocomplete should either be disabled or contextual.




### 2.3 All task variants show the same incorrect autocomplete behavior

The autocomplete issue inside the decision task is **not limited** to  
`new decision task`.

Testing shows that all three task creation options behave the same:

- **`tasks block`**
- **`tasks block`** (duplicate option)
- **`new decision task`**
- **`new service task`**
- **`new switch task`**

**Observed across all task types:**

- Autocomplete inside the created task block only works on the **first line**,  
  and the suggestions come from the **previous unrelated context**  
  (e.g., values from `type: STRING` in the inputs block).
- Lines such as:
  - `- TestingDecision:`
  - `- ServiceAsset:`
  - `- name:` (switch)
  - `decisionTable:`
  - `service:`
  - `switch:`
  
  …all receive autocomplete suggestions that do **not** belong to them.

- Inside the task bodies, fields like `id:`, `then:`, `ref:`, `inputs:`, etc.  
  **do not receive correct context-specific suggestions**.

**Expected:**

- Each task type should have its own context-aware autocomplete.
- The top-level task declaration lines (e.g., `- TestingDecision:`)  
  should either:
  - have no autocomplete, or
  - show only valid task-type suggestions.
- Nested fields of decision/service/switch tasks should receive  
  suggestions appropriate to that task type.

**Status:** ❌ **Bug – autocomplete context is incorrect for all task types**
The autocomplete engine appears to “inherit” context from the previous block  
(in this case an input block), and fails to switch to task-specific contexts  
for decision, service, and switch tasks.

## 3. Autocomplete inside service task input value produces duplicates and irrelevant options

### 3.1 Test scenario

**Flow content:**
```yaml
id: AutocompleteTestFlow3
description: service flow for autocomplete testing trying to emulate feedbackserviceflow

inputs:
  shouldBeQuestionnaireId:
    required: true
    type: STRING
    debugValue: "somenumberhere3243274627"
  workflowname:
    required: true
    type: STRING

tasks:

  - Dig_QuestionnaireCollector:
      id: dig_QuestionnaireCollector
      then: next
      service:
        ref: Dig_QuestionnaireCollector
        collection: false
        inputs:
          questionnaireId: 'autocomplete here'
```

Test location:  
`tasks[*].service.inputs.questionnaireId`  
(cursor placed inside `'autocomplete here'`)

---

### 3.2 Actual autocomplete results

Using autocomplete inside the value position (inside quotes) shows:

#### **Duplicated flow inputs**
- `flow input: shouldBeQuestionnaireId STRING`
- `flow input: shouldBeQuestionnaireId STRING` *(duplicate)*
- `workflowname: STRING`
- `workflowname: STRING` *(duplicate)*

#### **Three irrelevant “inputs block” suggestions**
- `inputs block`
- `inputs block`
- `inputs block`

These do **not** belong in a value position inside a service input.

#### **Duplicated task outputs**
- `task output: ‘something here1’`
- `task output: ‘something here1’` *(duplicate)*
- `task output: ‘something here2’`
- `task output: ‘something here2’` *(duplicate)*

Note: These appear only if the referenced service has defined outputs.

---

### 3.3 Why this is incorrect

**1. Multiple categories are duplicated**
- flow inputs appear twice  
- task outputs appear twice  
- `inputs block` appears three times  

**2. Wrong context for this position**
Inside a service input value, autocomplete should provide:

- flow inputs  
- possibly task outputs **once each**

NOT:
- structural inserts (`inputs block`)  
- duplicates  
- suggestions irrelevant to the value type  

**3. Expected behavior**
Autocomplete should list:

- `shouldBeQuestionnaireId`
- `workflowname`
- any valid task outputs  
- **only once each**
- **no block constructors** (like `inputs block`)
- **no service definitions**
- **no unrelated task suggestions**

---

### 3.4 Status

**Status:** ❌ **Bug – duplicated suggestions and irrelevant options in service input value context**

This is a clean case of autocomplete generating:
- duplicate items  
- unrelated structural items  
- incorrect context mixing  

It affects service input fields and likely other value-position contexts as well.
